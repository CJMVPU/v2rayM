# v0.5.7 early freeze and traffic-history catch-up

## Behavior

Replace the one-second departure grace with immediate freezing on AppKit's
`willResignActive`, `willHide` and `willMiniaturize` notifications. The watcher
latches impending resignation/minimization rather than trusting flags that still
report active/not-minimized during a will notification. It synchronously stops
presentation publication and broadcasts a window-scoped freeze to invalidate the
display link in the same notification turn. Repeated notifications cannot restart
it; an explicit thaw is sent only when the coordinator permits motion again.
Window detachment invalidates its link as well.

The existing surface remains mounted. Pending disc, card and row animations are
cancelled into their resting faces before departure; they do not keep executing
in the thumbnail. Disc activation still uses the solid side/back/shadow renderer
and the same timing/angle waypoints, with a cancellable task replacing uncancellable
keyframe runs. The 120 Hz preferred/maximum request remains unchanged.

Restoration waits for visible, non-minimized, active state and a 0.85-second quiet
interval. Window geometry/screen/occlusion events restart that interval while
returning. New departures cancel stale return tasks. The latest data and chart
replay are prepared synchronously before thaw; numeric/ring/content changes use
the existing 0.45-second transition and do not replay background card/row flips.

AppKit's public contract provides an impending activation-loss notification and
an impending minimization notification, not a public Stage Manager animation
start/end fence. Therefore this uses the earliest available will signals and a
conservative return-stability interval; it does not claim exact synchronization
with every compositor animation, altered animation speed, or OS release.
References: [willResignActive](https://developer.apple.com/documentation/appkit/nsapplication/willresignactivenotification),
[willMiniaturize](https://developer.apple.com/documentation/appkit/nswindow/willminiaturizenotification).

## Chart presentation

A presentation-only catch-up plan merges the retained frozen history with current
samples. A virtual display date advances monotonically from the frozen time to
live time, revealing the stored historical samples in chronological order. New
samples arriving during replay join the same timeline. Catch-up takes 0.65–2.4
seconds, bounded independently of absence length. Its scale interpolates too.
Clip-edge neighbours make curves scroll/reveal continuously; both segment IDs and
a 12-second gap guard prevent drawing invented connections across missing history
or node/core changes. No values are fabricated or written back into live sampling,
peaks, node totals or backend state. Storage is bounded to 2048 presentation samples.
A stopped core catches up to its stop time and does not start perpetual drawing.
Reduce Motion bypasses replay. Re-freezing retains the display clock's last date;
restarting a partially completed replay begins at its displayed virtual time.

## Validation and limits

Evidence: `artifacts/reviews/2026-11-17-freeze-057/`.

- Native suite: 204 executed, 200 passed, four existing optional checks skipped.
  Focused lifecycle/clock checks were rerun after the final attachment refinement.
  Helper suite: 63 passed. Product and DDD guards, signing and packaged loopback
  results are recorded separately in the product receipts.
- Tests cover synchronous will-miniaturize handling before the minimized flag,
  the latch across intermediate notifications, geometry deferring thaw, rapid
  direction changes, repeated early-freeze notifications, explicit clock thaw,
  detachment, background publication isolation, 120 Hz requests, chronological
  catch-up, bounded long absences, stopped-core behavior and gap/node boundaries.
- Live compositor screenshots preserve solid flip geometry. Release-mode paired
  offline apps exercised actual Stage Manager thumbnail/foreground changes with
  synthetic telemetry, without starting a proxy or changing installed app/data.
  Successful run evidence is in `candidate/stage-verified/` and
  `baseline/stage-verified/`; `freeze-results.json` and `analyze-freeze.py` summarize
  it. Exploratory runs are retained separately, including an early clock-latch
  regression that was corrected before acceptance.
- All six candidate will-resign events froze before did-resign and scheduled zero
  additional display callbacks. The notification-to-phase intervals were 1.3–14.4
  ms including synchronous JSON trace writes. The baseline's normal departure
  waited approximately one second and continued scheduling display callbacks.
- Candidate home mounted once, with no unmount during switching. Stable thumbnails
  issued zero display callbacks; returning resumed drawing. Three normal round
  trips and three rapid reversals were exercised. Four catch-ups recorded 70–142
  drawing evaluations each, monotonically advancing 3.5–19.5 seconds of stored
  history; unit tests verify exact convergence to the live/stop time. Drawing
  callbacks/evaluations are not compositor FPS or a dropped-frame measurement.
- Actual Dock minimization was attempted in normal/floating standalone fixtures,
  including a LaunchServices launch and the native minimize control. They did not
  report a minimized window or will/did-miniaturize events on this desktop. This
  is not counted as a successful real-minimization acceptance test. The early
  notification path and restoration latch are covered by regression tests.

The user authorized a version bump, signed local installer without replacing the
installed application, Git commit/push and old-build cleanup, without waiting for
remote CI. Installer mount/readback, installed-file hashes, push and cleanup have
separate receipts. No notarization or real-TUN acceptance is claimed.
